# AI Codebase Maintenance & Cleanup Guide

When operating in environments heavily generated by AI coding assistants (like Antigravity, Claude, or Cursor), the codebase can accumulate "AI generation artifacts." Because AIs prioritize generating isolated, functional code rapidly, they tend to leave behind redundant comments, unused imports, duplicated abstractions, and monolithic structures.

This document outlines the **Targeted Pruning & Comment Trimming** process, which is our official standard for maintaining maximum code efficiency and health without risking architectural breakage.

---

## 1. The Strategy: "Targeted Pruning & Comment Trimming"

This strategy is specifically chosen to resolve the low-hanging fruit of AI code generation—reducing bloat and improving readability—without undergoing high-risk logic restructuring or massive file splitting that could introduce regressions.

### The 4 Pillars of Targeted Pruning

#### Pillar 1 — Linter-Driven Import Pruning
AIs frequently hallucinate imports or leave behind imports from previous iterations (e.g., importing `GetStaticPaths` in Astro without actually using it, or importing `zod` schemas that were removed in a later prompt).

**How to detect:**
```bash
npx astro check          # For Astro projects
npx tsc --noEmit         # For strict TypeScript checking
npx eslint src/          # For standard JS/TS linting
```

**What to look for:**
- `ts(6133)` warnings — "X is declared but its value is never read"
- `import type { ... }` lines where the type is never referenced in the file
- Named imports from libraries that were experimented with but never used

**Rule:** If the compiler says it's unused, delete the import line. Do NOT delete the import if it's a side-effect import (e.g., `import './styles.css'`).

#### Pillar 2 — "Dead Stub" Function Removal
AI tools frequently generate utility wrapper functions for edge cases they *predicted* but never actually connected to the rest of the code. These become orphaned stubs that add cognitive noise.

**How to detect:**
```bash
# Search for function declarations and check if they're called anywhere
grep -rn "function " src/ --include="*.ts" --include="*.tsx" --include="*.astro"
grep -rn "const .* = (" src/ --include="*.ts" --include="*.tsx"
```

Then for each function name, search the codebase to confirm it's referenced somewhere else:
```bash
grep -rn "functionName" src/
```

**What to look for:**
- Helper functions defined in Astro frontmatter (`---` blocks) but never referenced in the template
- Utility functions in `lib/` files that no component imports
- Event handler functions defined but never bound to any element

**Rule:** If a function is defined but has zero call sites outside its own file, and it's not an exported API, delete it.

#### Pillar 3 — AI "Chat-Bot" Comment Trimming
AIs have a predictable habit of over-commenting. They write comments that restate the code verbatim instead of explaining the *intent* or *why* behind a decision.

**Bad comments (DELETE these):**
```typescript
// Loop through the services array
services.forEach(service => { ... });

// Set the state to true
setIsOpen(true);

// Return the response
return response;

<!-- Section container -->
<section>...</section>

/* ── Navigation Wrapper ──────────────── */
<nav>...</nav>
```

**Good comments (KEEP these):**
```typescript
// Cloudflare D1 doesn't support JOINs in this context,
// so we denormalize the data at write time instead
await db.insert(denormalizedTable).values(merged);

// Scale factor clamped to [1,3] to prevent GPU memory issues on mobile Safari
const newScale = Math.max(1, Math.min(dist / initialPinchDistRef.current, 3));

// ARCO compliance requires explicit consent before any analytics tracking
if (!hasConsent) return;
```

**The Litmus Test:** If the comment explains *what* the code does, delete it. If the comment explains *why* the code does it that way, keep it.

#### Pillar 4 — Unused Props, Variables & Dead CSS
AI iterations frequently leave behind:
- Destructured props that are never used in the component template
- CSS classes defined in `<style>` blocks but never applied to any element
- Variables declared in frontmatter that were part of a previous iteration

**How to detect:**
```bash
# Unused variables in TypeScript
npx tsc --noEmit 2>&1 | grep "is declared but"

# Unused CSS (manual review or use PurgeCSS)
# Look for <style> blocks and cross-reference class names with the template
```

## 2. Step-by-Step Cleanup Workflow

### Phase 1: Static Analysis (Automated)
```bash
# 1. Run the build to catch compile errors
npm run build

# 2. Run type checking for unused variable warnings
npx astro check    # or npx tsc --noEmit

# 3. Note all warnings — these are your cleanup targets
```

### Phase 2: Component-Level Manual Review
Go through each major component file and apply the 4 pillars:

**Checklist per file:**
- [ ] Remove unused imports at the top of the file
- [ ] Remove unused variables/props in the frontmatter or function signature
- [ ] Remove dead helper functions that have no call sites
- [ ] Trim comments that restate the code (keep comments explaining *why*)
- [ ] Remove empty `<style>` or `<script>` tags
- [ ] Remove `console.log()` / `console.warn()` debugging statements
- [ ] Remove `// TODO:` comments for tasks that have already been completed
- [ ] Remove commented-out code blocks (old iterations preserved "just in case")

### Phase 3: Verification
```bash
# Rebuild to confirm nothing broke
npm run build

# Run type checker again — warnings should be reduced
npx astro check
```

**Critical Rule:** Do NOT change any logic, restructure components, or split files during a pruning sweep. If a component is 1000 lines, it stays 1000 lines during this phase. Structural refactoring is a separate task with its own testing requirements.

## 3. Common AI-Generated Patterns to Watch For

| Pattern | Description | Action |
|---------|-------------|--------|
| **Orphaned imports** | `import { z } from 'zod'` with no `z.` usage below | Delete the import line |
| **Verbose block comments** | `/* ── Section Title ────── */` before self-evident HTML | Delete the comment |
| **Reflection comments** | `// We need to handle the edge case where...` followed by code that obviously handles it | Delete the comment |
| **Dead event handlers** | `function handleResize() {}` never bound to `addEventListener` | Delete the function |
| **Stale TODO markers** | `// TODO: Add error handling` when error handling already exists | Delete the comment |
| **Console debugging** | `console.log('debug:', variable)` | Delete the statement |
| **Commented-out code** | `// const oldApproach = ...` kept from a previous AI iteration | Delete the block |
| **Over-typed generics** | `Array<string>` where `string[]` suffices, or redundant type annotations on obvious literals | Simplify the type |
| **Redundant type casts** | `(value as string)` when `value` is already typed as `string` | Remove the cast |
| **Empty catch blocks** | `catch (e) {}` that silently swallow errors | Add proper error handling or `console.error` |

---

## 4. When NOT to Prune

- **Do NOT delete exported functions** — they may be used by other packages or future features
- **Do NOT delete environment variable references** — they may be used at runtime even if they look unused at build time
- **Do NOT delete `@ts-ignore` or `@ts-expect-error`** without understanding the underlying type issue
- **Do NOT delete comments that explain business logic** — ARCO compliance, GDPR requirements, Cloudflare-specific workarounds
- **Do NOT delete fallback/default values** — they exist to prevent runtime crashes when CMS data is missing

---

## 5. Why This Matters

| Benefit | Impact |
|---------|--------|
| **Token Efficiency** | Smaller files = fewer tokens consumed when AI agents read the codebase for future tasks |
| **Bundle Size** | Removing dead code and unused imports reduces the final JavaScript bundle shipped to users |
| **Developer Experience** | Clean code is dramatically easier for both humans and AI to navigate, understand, and modify correctly |
| **Maintenance Cost** | Less code = fewer things that can break, fewer things to update when dependencies change |
| **Onboarding Speed** | New contributors (human or AI) can understand the codebase faster without wading through noise |

---

## 6. Recommended Frequency

- **After every major feature migration:** Run a pruning pass on all touched files
- **Before every deployment:** Quick `astro check` / `tsc --noEmit` to catch new warnings
- **Monthly maintenance:** Full codebase sweep using all 4 pillars
- **After AI pair-programming sessions:** Review all files the AI modified for generation artifacts
